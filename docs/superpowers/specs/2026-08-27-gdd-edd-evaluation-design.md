# GDD EDD 测评流程设计

## 1. 目标

本设计只规范 GDD 产物的 EDD 测评。流程将生成或修改 GDD 的被测 Agent 与负责评分的 Cloud 隔离，固定每次测评使用的评分尺度，并把每次运行写入完全一致、可审计且可供用户直接阅读的目录结构。

测评必须能证明分数变化来自 GDD 工作流本身，而不是评分规则泄漏、历史失败案例、额外上下文或无关插件带来的收益。

## 2. 范围

本次包含：

- 每次只评价一份 GDD；
- AI 与人工使用固定三个维度评分；
- 精确记录评分输入、输出和执行参数；
- 生成一份面向用户的 Markdown 结果；
- 人工直接在 Markdown 中评分，不使用 Web 界面；
- 确定性校验并计算加权分数；
- 仅在出现阻断问题时生成问题记录。

本次不包含：

- 游戏构建、实际可玩性或运行质量评价；
- 玩家评分 Web；
- AI 基线采样和回归比较；
- 在正式测评上下文中使用 V1、V2、V3 失败案例；
- 每次运行时临时创建评分维度；
- 与 GDD 产物无关的工程质量评分。

## 3. 参与者与隔离边界

### 3.1 被测 Agent

被测 Codex 只接收普通用户需求和本次实验允许使用的 GDD 工具。每次运行必须创建全新 session，初始上下文为空，并且只启用批准的自研 MCP 白名单。

被测 Agent 不得收到：

- 三个评分维度；
- Rubric 或评分档位；
- Cloud 评分 Prompt 或输出 Schema；
- 历史失败案例或以前的测评结果；
- Superpowers 或其他无关插件。

启动器必须为每次被测运行生成隔离清单，至少记录新 session 标识、上下文来源列表、启用插件列表和 MCP 白名单。测评流程只接受上下文来源为空且插件列表符合白名单的运行；不能只依赖 Agent 自行声明“上下文已清空”。

### 3.2 Cloud AI 评分器

Cloud 只接收：

- 本次提交的 GDD；
- 固定 GDD Rubric；
- 固定评分 Prompt；
- 固定结构化输出 Schema。

Cloud 不得收到被测 Agent 的对话、历史案例、以前的分数、预期分数或工作流实现说明。它必须为每个固定维度输出分数、可定位的 GDD 证据、简要评分理由和证据缺口。

Cloud 可以报告额外发现，但这些发现不计分，也不能改变固定维度、满分或权重。

### 3.3 人工评分者

人工评分者读取 `result.md`，直接在文件预留位置填写三个维度的分数和评分理由。不开发 Web 或其他独立评分界面。

## 4. 固定评分模型

所有运行固定使用以下三个维度：

| 维度 | 满分 | 评价范围 |
| --- | ---: | --- |
| 体验价值 | 30 | 目标玩家、核心幻想、玩家动机、差异化、预期情绪与体验节奏 |
| 玩法与系统 | 40 | 核心循环、操作与选择、规则、反馈、难度、成长、经济和平衡 |
| 内容与呈现 | 30 | 内容结构、关卡、叙事、视觉、音频、UI、信息可读性和风格一致性 |

Rubric 负责定义评分档位和证据规则。表中的评价范围只是取证检查项，不拆成二级分数；AI 和人工均只填写三个维度总分。

AI 与人工使用同一套 `30 + 40 + 30` 刻度。每个维度按以下方式合并：

```text
合并维度分 = AI 维度分 * 0.40 + 人工维度分 * 0.60
最终总分 = 三个合并维度分之和
```

每个合并维度计算完成后四舍五入到一位小数。人工尚未填写时，AI 分数只能标记为“暂定 AI 评价”，不得输出最终分。

## 5. 固定目录结构

正式流程只引用一个生效版本的 Rubric、Prompt 和 Schema。

```text
docs/gdd-edd/
|-- README.md
|-- rubrics/
|   `-- gdd-v1.md
|-- prompts/
|   `-- evaluator-v1.md
|-- schemas/
|   `-- evaluation-v1.schema.json
`-- runs/
    `-- <evaluation-id>/
        |-- progress.md
        |-- result.md
        |-- problem.md                 # 可选
        `-- evidence/
            |-- request.json
            `-- response.json
```

旧模板、旧 Rubric、基线样本、玩家评分 Web 和以前的运行产物不进入正式执行路径。已跟踪的历史版本由 Git 历史保留；实现时不得自动删除现有未跟踪的用户文件。

## 6. 单次运行输出契约

### 6.1 `progress.md`

`progress.md` 是技术过程与审计记录，固定包含：

- 测评 ID 和状态；
- 开始时间、结束时间和耗时；
- 隔离清单路径及其校验结果；
- 本次启用的自研 MCP 白名单；
- Provider、模型和可观测生成参数；
- 三个维度的定义、评分档位和证据规则；
- AI/人工权重和计算公式；
- GDD、Rubric、Prompt、Schema 的路径、版本和 SHA-256；
- 实际发送给 Cloud 的完整消息，区分 system、developer、user 等实际角色；
- 原始请求、原始响应的路径和 SHA-256；
- Schema 校验、文件写入、回读和人工评分终结事件。

`progress.md` 不得包含历史案例、隐藏思维链、凭据、访问令牌或无关上下文。

### 6.2 `result.md`

`result.md` 是唯一一份面向用户的评价报告，不再生成“内部版 Result”。内容顺序固定为：

1. 测评状态和简要总结；
2. 评分摘要，包括维度、满分、AI/人工权重和公式；
3. AI 三维分数和暂定 AI 总分；
4. 每个维度的简要评价，包括证据、理由和证据缺口；
5. 不计分的补充发现（如有）；
6. 人工评分填写区；
7. 人工确认后生成的三个合并维度分和最终总分；
8. 最终结论和测评限制。

完整 Rubric 和完整技术 Prompt 不重复写入 `result.md`。Result 只展示用户理解分数所需的评分方法和本次理由。

人工填写区固定为：

```markdown
| 维度 | 满分 | AI | 人工 | 合并 |
| --- | ---: | ---: | ---: | ---: |
| 体验价值 | 30 | <AI 分数> | __ | 待计算 |
| 玩法与系统 | 40 | <AI 分数> | __ | 待计算 |
| 内容与呈现 | 30 | <AI 分数> | __ | 待计算 |
| 总分 | 100 | <AI 总分> | 自动计算 | 待计算 |

人工评分者：
人工评分时间：
人工评分理由：
最终结论：
```

人工总分由三个维度相加，不单独输入，避免总分与维度分不一致。

### 6.3 `problem.md`

`problem.md` 是可选文件，只在操作性问题阻止或使正常测评无效时生成，例如：

- 必需输入缺失或互相冲突；
- Cloud 或工具调用失败；
- 结构化输出不符合 Schema；
- 证据写入或回读失败；
- 人工分数超出范围；
- 存在无法给出可信分数的未解决阻断条件。

GDD 本身的缺点、扣分原因和证据缺口属于 `result.md`，不因此生成 `problem.md`。

### 6.4 `evidence/request.json`

请求证据保存 Cloud 实际收到的完整输入信封：

- 测评 ID；
- GDD 内容及其 SHA-256；
- Rubric 内容及其 SHA-256；
- 按角色分隔的完整消息数组；
- 输出 Schema 版本及其 SHA-256；
- Provider、模型和可观测生成参数；
- 隔离清单的校验结果。

请求证据不得包含被测 Agent 的历史对话或任何历史测评。

### 6.5 `evidence/response.json`

响应证据保存渲染 Markdown 前的 Cloud 原始结构化输出。该文件必须通过固定 Schema 校验，并保留原始维度分数、引用证据、评分理由、证据缺口和不计分的补充发现。

## 7. Prompt 与 Schema 契约

Cloud 评分 Prompt 必须明确要求：

- 只使用提交 GDD 中明确写出的证据；
- 严格使用三个固定维度和固定评分档位；
- 不推测实际手感、画面完成度、音频质量或运行稳定性；
- 每个维度都给出可定位证据和评分理由；
- 缺少信息时记录证据缺口，不自行补全；
- 同一根因不得跨维度重复加分或扣分；
- 补充发现单独输出且不计分；
- 只返回符合 Schema 的数据；
- 不创建或修改任何文件。

输出 Schema 必须要求：

- 来源标识；
- 严格三个维度对象，不多也不少；
- 每个维度有一个范围内分数；
- 每个维度至少一条带 GDD 定位的客观观察；
- 每个维度一段简要评分理由；
- 每个维度一个证据缺口列表；
- 可选的不计分补充发现列表。

Cloud 不决定目录名或 Markdown 结构。Runner 只接收结构化输出，校验后使用固定模板生成文件。

## 8. 执行流程

1. 创建新的测评 ID 和固定 Run 目录。
2. 读取并校验被测运行的隔离清单。
3. 通过显式路径加载 GDD、生效 Rubric、评分 Prompt 和输出 Schema。
4. 计算所有固定输入的 SHA-256。
5. 写入并回读 `evidence/request.json`。
6. 只把允许的请求信封发送给 Cloud。
7. 写入并回读 `evidence/response.json`。
8. 使用 Schema 和固定分值范围校验原始响应。
9. 生成 `progress.md` 和面向用户的暂定 `result.md`。
10. 人工在 `result.md` 填写三个维度分数和理由。
11. 运行无 Web 的 finalize 命令，校验人工字段、计算加权分数，并只更新 Result 中指定的计算字段。
12. 回读并校验全部必需产物。

## 9. 失败行为

评价开始前先创建 Run 目录和 `evidence/`。失败运行仍然生成：

- 状态为 `failed` 且记录最后完成步骤的 `progress.md`；
- 状态为“测评未完成”、不含最终分且有简要用户说明的 `result.md`；
- 已成功获得的请求或响应证据；
- 记录阻断原因和恢复动作的 `problem.md`。

流程不得把暂定 AI 分数展示为最终分。人工分数缺失、不是数字或超出对应维度范围时，finalize 必须失败，且不得改写任何已计算字段。

所有写入必须采用原子替换。流程声称运行或 finalize 成功前，必须回读全部必需产物并校验测评 ID。

## 10. 验证与测试

实现必须覆盖：

- 精确创建固定 Run 结构；
- 正常成功运行不生成 `problem.md`；
- 每类阻断失败都会生成 `problem.md`；
- 拒绝缺少或多出 AI 维度的响应；
- 拒绝超出范围的 AI 和人工分数；
- 正确计算 `40/60` 权重并保留一位小数；
- 人工 finalize 前不产生最终分；
- finalize 不改写 AI 评价正文；
- 请求/响应证据哈希正确且可成功回读；
- Cloud 请求不含历史案例、以前的结果或无关上下文；
- `result.md` 在不展示完整 Rubric 和技术 Prompt 时仍可独立理解；
- 玩家评分 Web 及其依赖不再进入正式执行路径。

## 11. 验收标准

满足以下条件时设计实现完成：

- 被测 Agent 在全新上下文中生成 GDD，且无法看到评分标准；
- Cloud 只使用固定的四类评分输入评价 GDD；
- 每个成功 Run 都在同一目录包含 `progress.md`、`result.md` 和两个证据 JSON；
- `problem.md` 只在出现操作性阻断时存在；
- 用户只读 `result.md` 即可理解本次评价；
- AI 分数始终附带证据和理由；
- 人工只需编辑 Markdown 即可评分；
- finalize 正确生成 `AI 40% + 人工 60%` 的最终分；
- 正式流程不需要 Web 服务；
- 历史失败案例和无关插件无法进入正式测评上下文。
