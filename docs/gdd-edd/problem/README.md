# 问题记录目录要求

## 1. 用途

本目录保存执行和评价过程中发现的疑惑点、证据缺口、输入冲突、工具失败及待人工判断事项。问题记录不得被正式评价结果覆盖或省略。

## 2. 必须进入问题记录的事项

- GDD 对核心玩法的定义存在歧义、矛盾或缺失；
- GDD 对 UI 视觉风格或可玩性的描述不足；
- 缺少实际游戏构建、运行记录或人工玩家反馈；
- 仅凭 GDD 无法判断实际可玩性或视觉效果；
- 人工评价模板缺失、版本不明或包含范围外维度；
- 工具调用失败、结果不完整或回读不一致；
- 输入文档、GDS 版本、GDD 版本或游戏构建不匹配；
- Claude 评分结论与证据冲突；
- 需要人工确认但尚未得到答案的其他事项。

## 3. 每个问题的记录要求

每个问题必须具有人工可引用的稳定编号，并记录：

- 问题标题；
- 发现阶段和发现者；
- 关联的两个评价维度之一；
- 事实和证据位置；
- 具体疑问；
- 对评分或后续执行的影响；
- 当前处理状态；
- 所需人工决定；
- 决定人、决定时间和决定内容（完成后）；
- 恢复执行的位置。

若一个问题不属于“核心玩法”或“玩家体验”，应先判断它是否与本次评价无关。与可维护性、可测试性等工程质量有关的问题不进入正式评分，但可以作为范围外备注保留。

## 4. 状态约束

问题状态只能表达事实状态，例如：

- `待人工判断`；
- `证据不足`；
- `已确认`；
- `已拒绝`；
- `已解决待复核`；
- `已关闭`。

AI 不得在没有人工决定或新证据的情况下，将“待人工判断”自行改为“已确认”或“已关闭”。

## 5. 与 Progression 和 Result 的关系

- Progression 在疑惑产生的步骤引用问题编号。
- Result 在证据不足或结论受限的位置引用问题编号。
- 人工回传决定后，先更新问题状态，再继续执行或重新评价。
- 问题记录是审查材料，不替代正式评价结果。
